# Streamlit Dashboard Suite

This directory contains the front-end application layer. It renders the processed analytical data from `output/` into an interactive dashboard.

## Architectural Overview
The front-end is structured into a primary entry point (`1_Home.py`) and a `pages/` directory containing the modular dashboard components. By separating the analytical processing (scripts) from the visual presentation (Streamlit), we ensure that the dashboard remains lightweight and doesn't perform heavy computations at runtime.

## The "Styling Battle": CSS & Theming
Getting the formatting right was the most challenging part of this project. Streamlit is excellent for rapid prototyping, but its default aesthetic is heavily opinionated, often resulting in "default grey" buttons and containers that didn't fit our custom deep-blue branding. 

* **CSS Injection:** To force our custom opaque-blue aesthetic (`rgba(11, 26, 48, 0.95)`), I had to inject raw CSS into every page using `st.markdown(unsafe_allow_html=True)`. This was a process of trial-and-error—using inspector tools to identify deeply nested Streamlit classes (like `div[data-baseweb="select"]`) and applying `!important` overrides to force the theme consistently.
* **Ligature Overlaps:** We encountered a specific bug where forcing custom fonts (Helvetica) caused Material Symbols (the expander icons) to render as raw ligature text. This was resolved by creating targeted CSS rules that explicitly re-map the icon font family just for those specific elements.

## The Navigation Architecture (`utils/navigation.py`)
Because the default Streamlit sidebar felt clunky and took up valuable horizontal space, we made a structural choice to hide the sidebar entirely (`initial_sidebar_state="collapsed"`). 

However, this left us without a built-in way to navigate between pages. `utils/navigation.py` is the solution to this problem:
* **Centralized Logic:** Instead of copying a header block into every single page (which would lead to maintenance nightmares), this module acts as a central control panel. 
* **Global Styles:** It houses the `apply_global_styles()` function, ensuring that the background, fonts, and CSS overrides are initialized uniformly the second a user lands on any page in the app.
* **Component-Based Navigation:** The `render_navigation()` function forces a consistent 7-column grid layout across the top of every page. If we need to add a page or change the link order, we only update this one file, and the entire app propagates the change instantly.

## Directory Structure
* **`pages/`**: Contains the modular dashboard components (Methodology, Historical/Modern Analytics, RAG Engine, Finals Predictor, Finals Matchup).
* **`utils/`**: Holds the global style and navigation logic.
* **`assets/`**: Contains the visual library, including team logos and the pre-compiled trajectory/comparison graphs generated by the scripts.

---

### Engineering Tip
If you are adding new pages, ensure you update the `render_navigation()` function in `utils/navigation.py`. Because we are using a custom 7-column layout, the column ratios (`st.columns([1.1, ...])`) are finely tuned to prevent text truncation on the "Historical Era" and "Modern Era" tabs. If you add an 8th page, you will need to re-balance these ratios to keep the top bar flush.
